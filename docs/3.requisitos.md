## 3.2. Requisitos Não-Funcionais

| **ID** | **Descrição** |
| --- | --- |
| RNF001 | O sistema deve utilizar mecanismos de autenticação e autorização, garantindo que cada usuário tenha acesso somente às funcionalidades, dados, conversas e recursos permitidos para seu perfil. |
| RNF002 | O sistema deve possuir interface simples e intuitiva, com navegação consistente, organização clara das funcionalidades, linguagem compreensível e execução das principais tarefas sem necessidade de treinamento específico. |
| RNF003 | O sistema deve possuir interfaces adequadas aos ambientes web e móvel, mantendo consistência de navegação e adaptação aos diferentes tamanhos de tela. |
| RNF004 | O sistema deve suportar pelo menos 500 usuários conectados simultaneamente sem comprometer o funcionamento das funcionalidades principais e mantendo tempo de resposta adequado para as operações realizadas. |
| RNF005 | O sistema deve permitir atualização de mensagens em tempo real sem necessidade de recarregamento manual da aplicação. |
| RNF006 | O sistema deve proteger mensagens e informações privadas contra acesso não autorizado durante o armazenamento e a comunicação entre os componentes da aplicação. |
| RNF007 | O sistema deve manter os dados armazenados de forma íntegra e consistente, garantindo especialmente a consistência dos vínculos entre padrinhos e apadrinhados após operações de criação, alteração ou encerramento. |
| RNF008 | O sistema deve tratar falhas de comunicação, indisponibilidade de serviços, timeouts e erros de cliente ou servidor, evitando que a falha de um componente comprometa o funcionamento geral da aplicação e utilizando estratégias de recuperação ou reenvio quando aplicável. |
| RNF009 | A arquitetura do sistema deve permitir expansão da quantidade de usuários, mensagens, serviços e dados armazenados sem exigir reestruturação completa da aplicação. |
| RNF010 | O sistema deve permitir que múltiplos clientes web e móveis se conectem ao servidor e realizem operações de forma concorrente, preservando a consistência dos dados. |
| RNF011 | O sistema deve possuir estratégias de testes que contemplem as funcionalidades críticas, integrações entre serviços e comunicação entre os componentes distribuídos da aplicação. |

## 3.3. Restrições Arquiteturais

As restrições impostas ao projeto que afetam sua arquitetura são:

- O sistema deverá adotar uma arquitetura baseada em microsserviços, com responsabilidades separadas entre os principais domínios da aplicação.
- O sistema deverá utilizar um modelo de comunicação baseado em Web Services, disponibilizando seus serviços por meio de uma API centralizada por um API Gateway.
- O back-end da aplicação deverá ser desenvolvido utilizando Node.js.
- O front-end web deverá ser desenvolvido utilizando React.
- O sistema deverá disponibilizar seus serviços para clientes web e mobile.
- A aplicação móvel deverá utilizar tecnologia móvel ou híbrida multiplataforma.
- O banco de dados relacional utilizado para persistência das informações estruturadas deverá ser o PostgreSQL.
- A arquitetura deverá utilizar mecanismos de mensageria para processamento assíncrono de eventos e mensagens em tempo real.
- O RabbitMQ deverá ser utilizado como broker de mensagens entre os serviços que necessitem de comunicação assíncrona.
- O sistema deverá utilizar Server-Sent Events (SSE) para envio de atualizações em tempo real do servidor para os clientes, conforme definido na arquitetura proposta.
- A comunicação entre microsserviços poderá utilizar gRPC quando houver necessidade de comunicação síncrona interna entre serviços.
- Arquivos e mídias deverão ser armazenados separadamente dos dados relacionais, utilizando um serviço de Object Storage.
- O sistema deverá permitir que múltiplos clientes se conectem simultaneamente ao servidor e realizem operações de forma concorrente.
- A arquitetura deverá prever tratamento de falhas de comunicação, indisponibilidade de serviços e timeouts, incluindo estratégias de recuperação e reenvio quando aplicável.
- O sistema deverá possuir estratégias de testes para os componentes e integrações da aplicação.
- Os serviços da aplicação deverão utilizar infraestrutura em nuvem.
- A aplicação web deverá ser disponibilizada em um serviço de hospedagem em nuvem gratuito, conforme exigido pela disciplina.

## 3.4. Mecanismos Arquiteturais

_Visão geral dos mecanismos que compõem a arquitetura do software baseando-se em três estados: (1) análise, (2) design e (3) implementação. Em termos de Análise devem ser listados os aspectos gerais que compõem a arquitetura do software como: persistência, integração com sistemas legados, geração de logs do sistema, ambiente de front end, tratamento de exceções, formato dos testes, formato de distribuição/implantação (deploy), entre outros. Em Design deve-se identificar o padrão tecnológico a seguir para cada mecanismo identificado na análise. Em Implementação, deve-se identificar o produto a ser utilizado na solução._

| **Análise** | **Design** | **Implementação** |
| --- | --- | --- |
| Persistência | Banco de dados relacional | PostgreSQL |
| Armazenamento de mídias | Armazenamento de objetos | Object Storage - provedor a definir |
| Front end Web | Aplicação web baseada em componentes | React |
| Front end Mobile | Aplicação móvel multiplataforma | Flutter |
| Back end | Arquitetura baseada em microsserviços | Node.js |
| Acesso aos serviços | API Gateway | Implementação a definir |
| Integração cliente-servidor | Web Service / API | Implementação a definir |
| Comunicação entre microsserviços | Comunicação síncrona entre serviços | gRPC |
| Mensageria | Comunicação assíncrona orientada a eventos | RabbitMQ |
| Comunicação em tempo real | Server-Sent Events | SSE Gateway |
| Autenticação e autorização | Controle de acesso baseado em usuários e perfis | Implementação a definir |
| Tratamento de erros | Tratamento de exceções, falhas de comunicação, timeouts e estratégias de reenvio | Implementação a definir |
| Log do sistema | Registro de eventos, erros e operações da aplicação | Implementação a definir |

| Deploy | Hospedagem dos serviços em ambiente de nuvem | Serviço em nuvem a definir |
